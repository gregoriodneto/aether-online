# Aether Online | INC-001 — API saudável no container, inacessível pelo host

**Tipo:** laboratório de troubleshooting (incidente simulado)  
**Stack:** Python/FastAPI, Uvicorn, Docker, Docker Compose, Linux, GitHub Actions  
**Status:** causa identificada; correção relatada como funcional

## 1. Contexto

O Aether Online é um projeto de laboratório para praticar infraestrutura de servidores de jogos. O serviço `game-server` expõe uma API FastAPI na porta 8000, empacotada em Docker e administrada por Docker Compose. O projeto também possui testes automatizados e pipeline de CI com GitHub Actions.

Foi introduzida intencionalmente uma falha de configuração para simular um incidente de conectividade.

## 2. Sintoma e impacto

Uma requisição feita no host não conseguia acessar o endpoint de saúde:

```bash
curl -i http://127.0.0.1:8000/health
# curl: (56) Recv failure: Conexão fechada pela outra ponta
```

Apesar disso, o Docker informava que o container estava em execução e saudável:

```text
aether-game-server   aether-game-server:1.2   Up (healthy)   127.0.0.1:8000->8000/tcp
```

**Impacto no laboratório:** o serviço não era acessível pelo endpoint publicado no host, embora o healthcheck interno obtivesse sucesso.

## 3. Evidências coletadas

| Verificação | Evidência | Interpretação |
|---|---|---|
| `curl` no host | `curl: (56) Recv failure` | A chamada ao endpoint publicado falhava. |
| `docker ps` | `Up (healthy)` | O container estava ativo e o healthcheck passava. |
| `docker logs -f aether-game-server` | `Uvicorn running on http://127.0.0.1:8000` | O servidor escutava apenas no loopback interno do container. |
| Logs do healthcheck | `GET /health HTTP/1.1" 200 OK` | A verificação interna alcançava o serviço. |
| `docker port aether-game-server` | `8000/tcp -> 127.0.0.1:8000` | O Docker publicava a porta no loopback do host. |
| Execução local do Uvicorn na porta 7000 | `curl http://127.0.0.1:7000/health` → `200 OK` | A aplicação funcionava fora do container. |
| `docker exec ... ss -lnt` | `ss: executable file not found` | A imagem slim não continha essa ferramenta de diagnóstico. |

Foi também tentado o acesso ao IP `172.20.0.2` do container; as tentativas falharam. Esse resultado, isoladamente, não prova a causa, pois depende do contexto da rede e do momento do teste.

## 4. Causa raiz

O Uvicorn havia sido iniciado com `--host 127.0.0.1`. Dentro de um container, esse endereço é o loopback **do próprio container**. O processo aceitava chamadas internas, mas não estava escutando na interface de rede usada pelo encaminhamento da porta publicada pelo Docker.

O healthcheck não detectou a indisponibilidade externa porque consultava `127.0.0.1:8000/health` **de dentro do container**.

## 5. Correção aplicada

No serviço `game-server` do Compose, a inicialização passou a usar `--host 0.0.0.0`:

```yaml
game-server:
  image: aether-game-server:1.2
  container_name: aether-game-server
  build:
    context: ../services/game-server
    dockerfile: Dockerfile
  ports:
    - "127.0.0.1:8000:8000"
  command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
  restart: unless-stopped
  networks:
    - aether-network
```

`0.0.0.0` faz o servidor escutar em todas as interfaces IPv4 do container. Já `127.0.0.1:8000:8000` limita a publicação da porta ao loopback do host, adequado para este laboratório local.

Após o ajuste, o operador relatou que o endpoint voltou a responder. O registro fornecido inclui uma inspeção do comando efetivo:

```text
["uvicorn","app.main:app","--host","0.0.0.0","--port","8000"]
```

**Nota de evidência:** a transcrição compartilhada contém tentativas com falha e testes locais bem-sucedidos, mas não inclui a saída final do `curl` na porta 8000 após a correção. Para fechar o relatório com comprovação reproduzível, anexar esse teste final.

## 6. Lições aprendidas

1. `healthy` não garante que um serviço esteja acessível pelo caminho usado pelo cliente.
2. O loopback de um container é diferente do loopback do host.
3. A publicação de portas pelo Docker e o endereço em que a aplicação escuta são configurações distintas.
4. Logs, testes internos/externos e inspeção da configuração efetiva ajudam a isolar a causa raiz.
5. Imagens mínimas podem não incluir utilitários como `ss`; isso deve ser considerado no plano de diagnóstico.

## 7. Prevenção e próximos passos

- Adicionar ao pipeline um teste de integração que suba o container e execute `curl` pelo host na porta publicada.
- Manter o healthcheck interno para indicar o estado do processo, mas complementar com uma verificação externa de disponibilidade.
- Documentar a diferença entre `CMD` do Dockerfile e `command` do Compose, que o substitui.
- Preservar evidências de antes e depois, com saídas do `curl`, `docker ps`, logs e configuração efetiva.

## 8. Evidências a anexar

- Captura do GitHub Actions com jobs `test` e `docker-build` aprovados.
- Saída do `docker ps` mostrando `healthy` durante a falha.
- Trecho do log `Uvicorn running on http://127.0.0.1:8000`.
- Teste `curl` falhando no host antes da correção.
- Teste `curl` retornando HTTP 200 no host depois da correção (a coletar).
